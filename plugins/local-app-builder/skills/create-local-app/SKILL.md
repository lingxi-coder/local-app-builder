# Create or modify a local app

Load the host's built-in `local-app` skill first when available. Its tool schema and host capability contract are authoritative. Desktop, Android and iOS share manifest schema 2. Execution targets and native capabilities remain platform-specific.

## Schema-2 project flow

When `LocalApp` advertises `bundle_path`, use the project flow. A local app may be a static page, a multi-file Vite/TypeScript project, or a frontend with Node/Python/local-command backends. Network access, modules, workers and declared native capabilities are supported. Do not impose single-HTML or offline-only requirements when the host supports projects.

1. Converge the user's requirements. If they already gave a clear request or approved a plan, proceed without repeating approval. Use the installed frontend-design, accessibility, React and engine skills when relevant.
2. Inspect the current host with its permitted shell tool (Bash or Shell). Use project-local npm/pnpm/Bun dependencies, Python virtual environments and lockfiles. Do not modify a shared Mobile Linux toolchain; if its managed execution runtime is missing, use the native runtime settings. Follow existing host permission mechanisms.
3. Use an existing project or an appropriate scaffold. The bundled catalog at `${LINGXI_SKILL_DIR}/../../assets/templates/catalog.json` is optional. Its five templates remain useful for single-file artifacts, but projects may choose other frameworks and ordinary multi-file builds.
4. Write schema-2 `lingxi-app.json` using the host skill's manifest contract: explicit targets, package source allowlist/lockfiles and data compatibility. Record repeatable install/build steps, process commands, virtual environments, dependencies between services, and readiness checks. Servers bind to `127.0.0.1` and read their assigned `PORT`. Keep durable data in `LOCAL_APP_DATA_DIR` or browser storage.
5. Run the project and verify it with existing browser tools/skills. Test the user's important interactions, reload/storage behavior and errors. For a backend, also verify its readiness endpoint and logs.
6. Call `LocalApp` with `bundle_path`. Updating uses the same app `id` plus the latest `expectedRevision` from `read`. Call `start`, inspect `status` and `logs`, and test the registered app in its actual platform container (Desktop window; the system-selected external browser on Mobile). Deliver the app card and its entry in Apps; a source path or a temporary development server alone is not delivery.

First publication does not grant permissions. The native Apps host asks for requested capabilities and exact-release execution consent. A later launch reuses its recorded install/start recipe without a creating-chat model. New code digests do not inherit existing capability grants. Desktop closing normally stops its application task. Mobile application pages open in the external system browser, never an embedded WebView. Closing the native management page does not close a browser tab or stop its run: use the explicit Stop action. Android uses a user-visible running notification; iOS has only its finite system background budget and explicitly pauses on expiry. Do not promise an always-running local server. Quitting LingXi stops local app processes.

## Apps that call an Agent

When an app needs image recognition, structured model output or authorized tool use, read `${LINGXI_SKILL_DIR}/references/host-agent.md`. Use `window.localApp.agent` only when the current host skill advertises it. The host runs an independent task with its selected model and explicit tool grants; the app must not embed provider keys or reuse the chat that created it. Do not use Remote Control as a same-device Agent API.

When authoring a tool-enabled app, call `LocalApp({"action":"agent_catalog"})` from the creating chat to discover public model and exact opaque tool IDs. This read-only catalog requires no app ID, contains no connection configuration or credentials, and grants no permission. Declare requested tool IDs in the release and let the user authorize them in Apps. A packaged Skill is an instruction file declared by `{ "id": "summary", "path": "skills/summary/SKILL.md" }`; callers select it by ID in `input.skills`. A Skill does not grant tools. The runtime rechecks the release, host grant, request, platform and enterprise policy for every turn.

Start from `${LINGXI_SKILL_DIR}/../../assets/examples/desktop-calorie-agent` for a choose-photo → structured result → editable portions → explicit save example. Copy it into a new project before editing; publish the complete directory with `bundle_path`. The app uses browser `File` objects and the generic attachment API. Its nutrition estimates and recording logic belong to the app, not to the generic host API. For persistent attachment-backed Chat patterns, use `${LINGXI_SKILL_DIR}/../../assets/examples/attachment-chat-skill`.

`localApp.agent.run(input)` resolves to the final `AgentReply`. Use `localApp.agent.tasks.start(input)` when the app needs an early `runId`, progress, cancellation or durable restore; `get`, `list` and `subscribe` read the host-owned task ledger. JavaScript Promises do not survive reload. Reload reconnects through `tasks.list/get` and persistent Chat history; never auto-resubmit from page startup. Store only the app's draft state needed for an explicit user retry, with the same request ID and file contents.

Use `localApp.files.pick({multiple,accept})` or standard file inputs. Pass selected browser `File` objects in `attachments`; do not construct base64 image objects or pass paths. A request uploads metadata and binary parts together once, with at most eight files, 25 MiB per file and 50 MiB total. Native model limits can be lower. The browser SDK keeps a pending iOS request and its files in IndexedDB during the foreground wake-and-return handoff. It submits only after LingXi returns with the matching request ID marker; ordinary reload never replays it. Keep the final action user initiated and preserve the same request ID when the user confirms a retry.

Persistent Chats are App-owned conversations. `chats.create/open/list/archive/delete` manage them; a Chat handle provides `send`, `history`, `subscribe` and `cancel`. Use the durable Chat ID to reopen after refresh. Handle all task terminal states, failed capability checks, denial and cancellation. Display only validated structured output on `succeeded`. Keep approvals and questions in the trusted host UI. Generated pages must not call model providers directly or contain provider keys. Test both the registered app and configured model; unit tests and standalone browser rendering are not end-to-end proof.

## Mobile targets and standalone documents

Static schema-2 projects may target mobile `web` without a Linux service. Node/Python/process projects require the available Mobile Linux execution environment, compatible architecture/channel and native exact-release consent. Do not assume Desktop executables, arbitrary host paths or undeclared device APIs exist on a phone. Use `localApp.serviceUrl/serviceSocketUrl` for registered app services rather than hardcoding ports.

Mobile pages run in the actual system-selected external browser, not an embedded WebView/WKWebView. Detect capabilities such as IndexedDB, file selection, camera capture and recovery from browser APIs; do not branch on browser brand or package name. Load the host SDK before application calls: `if (!globalThis.localApp) await import('/__local_app_sdk.js')` from the app's main module. Desktop retains its preload SDK. `localApp.files.pick()` returns browser `File` objects; send them as `attachments` without converting to base64.

The host derives App and run identity from its current route; page-owned IDs cannot select another app or host operation. App pages cannot configure models/grants or approve tools. Use `localApp.host.open()` from an explicit user action to return to trusted LingXi approvals. The SDK handles the iOS foreground wake-and-return handoff and submits the complete request only after the matching readiness marker; no prompt, files or credentials go in the link. The SDK also installs an app-origin-scoped recovery worker when supported. It fetches live navigations first and caches only its fixed offline recovery page; it never caches app pages, POSTs or Agent results. That page lists saved request IDs and provides user-confirmed return links to LingXi. Check `localApp.info().recovery.status` and listen for `localApp:recovery-unavailable`; tell the user when recovery is not supported while keeping online use available. The SDK retains pending prompt/file data for at most 24 hours and accepted idempotency receipts for 7 days, subject to 32-record and 100 MiB limits. It deletes expired records without replaying them and clears its copy immediately when the host definitively rejects admission. Apply similar expiry to any App-owned retry draft, and clear that copy on definitive rejection. Display connection failures as host unavailable/paused, preserve drafts only for explicit retry, and never silently replay a task on ordinary reload. Do not claim indefinite Mobile background Agent execution. Browser storage belongs to the external browser; stopping/removing an app does not clear that storage.

For a simple static document, the current host may wrap `html`/`file_path` into schema 2. Agent/device declarations need a project manifest. No schema-1 manifest or old mobile document runtime is generated. Without LocalApp, a standalone browser page is a preview or browser deliverable and must be described accordingly.

## Modify and recover

Use LocalApp list/read to locate the app, edit its authoring source, test, and republish to the same id with expectedRevision. If authoring source is unavailable, use native Customize/Remix; never edit the immutable release snapshot. Preserve data and explain application data migrations when needed. Use status/logs to diagnose installation or startup failures, repair with Bash, and republish. Do not clear application data as a repair step.
