# Create or modify a local app

Load the host's built-in `local-app` skill first when available. Its tool schema and host capability contract are authoritative. Desktop, Android and iOS share manifest schema 2. Execution targets and native capabilities remain platform-specific.

## Schema-2 project flow

When `LocalApp` advertises `bundle_path`, use the project flow. A local app may be a static page, a multi-file Vite/TypeScript project, or a frontend with Node/Python/local-command backends. Network access, modules, workers and declared native capabilities are supported. Do not impose single-HTML or offline-only requirements when the host supports projects.

1. Converge the user's requirements. If they already gave a clear request or approved a plan, proceed without repeating approval. Use the installed frontend-design, accessibility, React and engine skills when relevant.
2. Inspect the current host with its permitted shell tool (Bash or Shell). Use project-local npm/pnpm/Bun dependencies, Python virtual environments and lockfiles. Do not modify a shared Mobile Linux toolchain; if its managed execution runtime is missing, use the native runtime settings. Follow existing host permission mechanisms.
3. Use an existing project or an appropriate scaffold. The bundled catalog at `${LINGXI_SKILL_DIR}/../../assets/templates/catalog.json` is optional. Its five templates remain useful for single-file artifacts, but projects may choose other frameworks and ordinary multi-file builds.
4. Write schema-2 `lingxi-app.json` using the host skill's manifest contract: explicit targets, package source allowlist/lockfiles and data compatibility. Record repeatable install/build steps, process commands, virtual environments, dependencies between services, and readiness checks. Servers bind to `127.0.0.1` and read their assigned `PORT`. Keep durable data in `LOCAL_APP_DATA_DIR` or browser storage.
5. Run the project and verify it with existing browser tools/skills. Test the user's important interactions, reload/storage behavior and errors. For a backend, also verify its readiness endpoint and logs.
6. Call `LocalApp` with `bundle_path`. Updating uses the same app `id` plus the latest `expectedRevision` from `read`. Call `start`, inspect `status` and `logs`, and test the registered app in its actual platform container (Desktop window; the system-selected external browser on Mobile). Deliver the app card and its entry in Apps; a source path or a temporary development server alone is not delivery.

First publication does not grant permissions. The native Apps host asks for requested capabilities and exact-release execution consent. A later launch reuses its recorded install/start recipe without a creating-chat model. New code digests do not inherit existing capability grants. Desktop closing normally stops its application task. Mobile application pages open in the external system browser, never an embedded WebView. Closing the native management page does not close a browser tab or stop its run: use the explicit Stop action. Android uses a user-visible running notification; iOS has only its finite system background budget and explicitly pauses on expiry. Do not promise an always-running local server. Quitting LingXi stops local app processes.

## Apps that call an Agent

When an app needs image recognition, structured model output or host-authorized tools, read `${LINGXI_SKILL_DIR}/references/host-agent.md`. Use `window.localApp.agent` only when the current host skill advertises it. The host selects the model and owns credentials, execution, approvals and questions. The app must not embed provider keys or reuse the chat that created it. Do not use Remote Control as a same-device Agent API.

Use AG-UI 1.0 types and client semantics: `RunAgentInput`, `Message`, `ContentPart`, `BaseEvent`, and the official `AbstractAgent` client. Use the protocol's standard types and event union. AG-UI run identity is `threadId` plus caller-supplied `runId`; use a fresh thread for a standalone run and a host Chat's stable ID for a persistent conversation. A reload restores messages or attaches read-only to the existing thread; it must not call `runAgent()` until the user submits a new turn.

Host-specific settings belong only in `RunAgentInput.forwardedProps['com.lingxi.localApp']`, with `{version:1, outputSchema?, tools?, skills?, maxTurns?, timeoutMs?}`. Discover exact opaque public host tool IDs with `LocalApp({"action":"agent_catalog"})` in the creating chat. The catalog is read-only and grants no permission. Request those IDs in the namespaced `tools` option and let the user authorize them in trusted Apps UI. AG-UI's top-level `RunAgentInput.tools` represents app-provided frontend tools that the app itself executes; this runtime does not support top-level `tools`, `context`, `state` or `resume`, and rejects them when they are sent. A packaged Skill is an instruction file declared by `{ "id": "summary", "path": "skills/summary/SKILL.md" }`; select it in the namespaced `skills` option. A Skill grants no tools. The runtime rechecks release, host grant, platform and enterprise policy on every run.

The stateless first-release profile accepts exactly one user `Message` on a fresh thread/run. Use a host Chat resource for multi-turn history. Although AG-UI defines other part sources and modalities, this profile supports text and the image/document `ContentPart` returned by `agent.file(file)`; it rejects remote URL and provider file handles, audio/video parts and unsupported top-level state/context/resume/frontend-tool inputs.

Start from `${LINGXI_SKILL_DIR}/../../assets/examples/desktop-calorie-agent` for a choose-photo → structured result → editable portions → explicit save example. Copy it into a new project before editing; publish the complete directory with `bundle_path`. For persistent attachment-backed threads, use `${LINGXI_SKILL_DIR}/../../assets/examples/attachment-chat-skill`.

Pass browser `File` objects through `localApp.agent.file(file)` and place the returned official `ContentPart` in a user `Message.content` array beside `{type:'text',text}` parts. Never invent a path, hand-build provider file handles, or base64-encode files in app code. Use `localApp.files.pick({multiple,accept})` or a standard file input. Keep prompts and file bytes out of URLs. App-specific schemas and invariants must be validated before rendering or saving; protocol or host validation does not replace application checks.

Treat incoming values as official `BaseEvent` members. `RUN_ERROR` is a protocol event and may arrive without making the `runAgent()` Promise reject, so handle its subscriber callback as a failure. A fulfilled `RunAgentResult` contains `result` and `newMessages`; do not infer a structured result by scraping assistant Markdown. On cancellation, inspect the terminal `RUN_FINISHED.outcome` and report success only for the success outcome. `abortRun()` is an explicit cancellation request, not proof the run was cancelled. Keep approval and question flows in the trusted host UI. Generated pages must not call model providers directly or contain provider keys. Test the registered app and configured model; unit tests and standalone browser rendering are not end-to-end proof.

## Mobile targets and standalone documents

Static schema-2 projects may target mobile `web` without a Linux service. Node/Python/process projects require the available Mobile Linux execution environment, compatible architecture/channel and native exact-release consent. Do not assume Desktop executables, arbitrary host paths or undeclared device APIs exist on a phone. Use `localApp.serviceUrl/serviceSocketUrl` for registered app services rather than hardcoding ports.

Mobile pages run in the actual OS-selected external browser, not an embedded WebView/WKWebView. Detect capabilities such as IndexedDB, file selection, camera capture and recovery from browser APIs; do not branch on browser brand or package name. Load the host SDK before app calls with `if (!globalThis.localApp) await import('/__local_app_sdk.js')` from the app's main module. Desktop retains its preload SDK. `localApp.files.pick()` returns browser `File` objects; convert each with `localApp.agent.file(file)` and place the returned official `ContentPart` in the user's `Message`.

The host derives App identity from its current route and validates `threadId` and `runId` within that App. App pages cannot configure models/grants or approve tools. Use `localApp.host.open()` only from an explicit user action to return to trusted LingXi approvals. The SDK handles the iOS foreground wake-and-return handoff and submits the complete, saved AG-UI input only after the matching `runId` readiness marker; prompts, file bytes and credentials never go in the link. The app-origin-scoped recovery worker fetches live navigations first and caches only its fixed offline recovery page; it never caches App pages, Agent requests or results. Check `localApp.info().recovery.status` and listen for `localApp:recovery-unavailable` when showing recovery support.

The SDK retains pending full inputs for at most 24 hours and accepted run-ID receipts for 7 days, subject to 32-record and 100 MiB storage limits. It expires old inputs without replay and clears its copy after definitive host rejection. On iOS, retain the same `RunAgentInput.runId` through foreground handoff. Ordinary reload does not submit an App-owned draft; use read-only history/events to restore and require an explicit user action for a retry with the same run ID and unchanged input. Report a cancelled terminal outcome as cancelled, never success. Do not claim indefinite Mobile background Agent execution: Android keeps its user-visible runtime notification, and iOS uses a finite foreground continuation lease that may expire. Browser storage belongs to the external browser; stopping/removing an App does not clear that site data.

For a simple static document, the current host may wrap `html`/`file_path` into schema 2. Agent/device declarations need a project manifest. No schema-1 manifest or old mobile document runtime is generated. Without LocalApp, a standalone browser page is a preview or browser deliverable and must be described accordingly.

## Modify and recover

Use LocalApp list/read to locate the app, edit its authoring source, test, and republish to the same id with expectedRevision. If authoring source is unavailable, use native Customize/Remix; never edit the immutable release snapshot. Preserve data and explain application data migrations when needed. Use status/logs to diagnose installation or startup failures, repair with Bash, and republish. Do not clear application data as a repair step.
